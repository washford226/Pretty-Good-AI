The voice bot is intentionally built as a thin orchestration layer around a few clear responsibilities: Twilio call initiation, patient-scenario steering, transcript capture, and issue triage. A minimal FastAPI service exposes the webhook endpoints used by Twilio, while the scenario catalog defines the realistic patient intent, expected follow-up questions, and the likely failure modes we want to test. This makes the system easier to reason about and easier to iterate on without introducing unnecessary infrastructure complexity.

I chose this architecture because the challenge is mostly about conversational quality and bug-finding rather than heavyweight deployment work. A lightweight HTTP service keeps the app easy to run locally, easy to debug, and straightforward to adapt when new edge cases show up. It also fits the assessment’s goal: we can quickly modify the patient scripts, record each call, and document the exact conversational mistakes the AI makes so they are clear, reproducible, and valuable to a reviewer.

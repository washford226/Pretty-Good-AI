This project uses a simple webhook architecture: Twilio places the outbound call and sends speech events to a local FastAPI app, ngrok exposes that local app to the public internet, and OpenAI generates the patient-side responses for each turn. Each call is keyed by Twilio CallSid in memory so turn history is preserved across webhook requests, and we persist two outputs per call: transcript JSON and MP3 recording. This design is intentionally thin so iteration is fast while still producing the exact artifacts needed for review.

Twilio was chosen because it solves telephony reliably out of the box: call creation, speech gathering, and recording callbacks are all first-class features with predictable webhook behavior. Upsides: production-grade phone infrastructure, fast setup, and straightforward event hooks for automation. Downsides: speech recognition and call timing are not fully deterministic (occasional missed words or overlap), and telephony plus recording costs can add up across many test runs.

ngrok was chosen because this project is developed locally and Twilio requires a public HTTPS callback URL. Upsides: instant tunnel, no cloud deployment ceremony, and quick iteration during debugging. Downsides: tunnel URLs can rotate, added network hop can introduce slight latency, and local-machine availability becomes part of runtime reliability.

OpenAI was chosen because it is the model stack I have used in previous projects, which reduced implementation risk and let me focus on conversation quality and bug discovery. In practice, familiarity mattered more here than model experimentation: the challenge rewards coherent voice interactions and useful bug findings, so choosing a known API helped me ship faster, tune prompts faster, and spend more time on call quality analysis.
